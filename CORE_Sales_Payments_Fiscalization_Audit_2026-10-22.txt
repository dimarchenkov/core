============================================================
A. EXECUTIVE SUMMARY
============================================================

Итог аудита: текущая реализация заметно надёжнее браузерно-управляемого checkout, но ещё не гарантирует безопасное восстановление после неоднозначного ответа AQSI. Для реальной точки продаж есть три подтверждённых P0-класса риска.

1. VERIFIED — повторная фискализация после неопределённого POST.

Если POST /Receipts/process мог выполниться, но CORE не получил operationId, Fiscalization становится UNKNOWN, однако worker продолжает цикл и снова вызывает создание чека. Для наличных lookup всегда возвращает None, поэтому риск особенно прямой.

Evidence:
- src/core/sales/checkout.py — CheckoutService.process_fiscalization(), _initiate_fiscalization(), _record_fiscal_error()
- src/core/sales/fiscalization_jobs.py — run_fiscalization_job()
- src/core/integrations/aqsi/checkout.py — AqsiCheckoutAdapter.find_fiscalization()

2. VERIFIED + INFERRED impact — AQSI HTTP 5xx трактуется как определённый отказ.

AqsiHttpClient._request() ставит retryable, но не outcome_unknown. Sales переводит попытку в FAILED, возвращает Sale в DRAFT и разрешает новую оплату. Если AQSI успел принять команду до ответа 500, возможен второй charge. Аналогично возможен второй чек после ручного retry.

Evidence:
- src/core/integrations/aqsi/client.py — AqsiHttpClient._request()
- src/core/sales/checkout.py — CheckoutService._record_payment_error()

3. VERIFIED — финансовые backup-артефакты уже добавлены в Git index с mode 100644, а master encryption key находится незатреканным под backups/.

Содержимое ключа не читалось. .gitignore не исключает эти файлы. Это риск утечки production-данных и ключа при следующем commit/push.

Положительные стороны:

- VERIFIED: Payment и fiscal jobs хранятся в PostgreSQL; Redis — только механизм пробуждения.
- VERIFIED: Browser больше не выполняет provider polling и может быть закрыт.
- VERIFIED: Неопределённая card payment без external_id блокирует слепой повтор.
- VERIFIED: Stock posting и создание fiscal job выполняются в транзакции с фиксацией успешной оплаты.
- VERIFIED: Повторные движения склада ограничены уникальным индексом.
- VERIFIED: В текущей БД нет completed Sales без успешной effective payment, корректной fiscalization либо inventory timestamp.

Общий вердикт: необходимо устранить P0 до доверия автоматическим retry при неопределённом POST. Обычный happy path реализован, но end-to-end физическая надёжность остаётся UNVERIFIED, потому что live-device UAT не выполнялся.

============================================================
D. CURRENT STATE MACHINES
============================================================

D1. Sale

DRAFT ------------------------------> CANCELLED
  |
  +-- card --> PAYMENT_PENDING
  |                 |
  |                 +-- failed/canceled --> DRAFT
  |                 +-- succeeded -------> PAID
  |
  +-- cash ------------------------------> PAID
                                            |
                    no receipt -------------+--> COMPLETED
                                            |
                    receipt required        v
                                  FISCALIZATION_PENDING
                                    |                 |
                                    | success         | definite failure
                                    v                 v
                                COMPLETED      FISCALIZATION_FAILED
                                                     |
                                                     +-- explicit retry
                                                         -> FISCALIZATION_PENDING

- VERIFIED: PAYMENT_FAILED существует в enum, но текущий checkout его не устанавливает. В БД осталась Sale #1 в этом состоянии; list_drafts() её не возвращает. Это legacy stuck state.
- VERIFIED: COMPLETED зависит от успешного/пропущенного fiscalization, то есть коммерческое завершение и фискальная обязанность связаны слишком жёстко.
- VERIFIED: База не запрещает противоречивые межтабличные сочетания статусов.

D2. PaymentAttempt

PENDING -> PENDING | UNKNOWN | SUCCEEDED | FAILED | CANCELED
UNKNOWN + external_id -> provider polling
UNKNOWN без external_id -> manual reconciliation required; automatic retry blocked
FAILED/CANCELED -> новый PaymentAttempt только через explicit retry

UNKNOWN сохраняется правильно для transport timeout/request error. Но HTTP 5xx ошибочно попадает в FAILED.

D3. Fiscalization

PENDING -> PENDING | UNKNOWN | SUCCEEDED | FAILED
FAILED -> PENDING через explicit retry
SKIPPED -> terminal

Опасный переход: UNKNOWN без external_id -> повторный initiate, хотя предыдущее создание могло выполниться.

D4. Background jobs

QUEUED -> PROCESSING -> COMPLETED | FAILED | QUEUED
stale PROCESSING -> QUEUED

Исключение: stale payment job без provider ID переводится в FAILED, Payment — в UNKNOWN. У job нет состояний manual_review, canceled или lease ownership.

============================================================
E. DEPENDENCY AND MODULARITY ASSESSMENT
============================================================

- Sales -> Catalog/Pricing: appropriate domain dependency — выбор товара и frozen price snapshots.
- Sales -> Inventory: appropriate application dependency, хотя синхронное stock posting внутри payment completion увеличивает blast radius.
- Sales -> generic provider protocols: appropriate infrastructure boundary.
- Sales models -> IntegrationProvider: infrastructure leakage; provider enum сохраняется прямо в financial domain.
- FiscalizationJob.aqsi_operation_id: архитектурное нарушение generic boundary.
- CheckoutProviderFactory: composition root расположен правильно, но _build() поддерживает только AQSI и требует, чтобы одна Integration предоставляла одновременно payment и fiscal capabilities.
- AQSI adapter -> Sales provider DTO: нормальная зависимость инфраструктурного адаптера от порта.
- AQSI incident recovery -> Sales/Inventory models: допустимо только как одноразовый recovery tool; повторное использование сделает его boundary violation.

Ответы на ключевые вопросы:

- Sales application service напрямую AQSI client не вызывает: нет.
- Создать payment без AQSI можно: да, только cash.
- Безопасно завершить Sale через внешнюю кассу: нет; cash_without_receipt не хранит внешний provider/device/receipt и искажает происхождение платежа.
- Bank operation details находятся в отдельном PaymentAttempt, а не в полях Sale: да, это хорошо.
- Fiscalization связана с Sale completion: да, чрезмерно.
- Feature toggle Sales отсутствует. Sales routes и UI подключаются безусловно; SPA после login обязательно вызывает /api/sales.
- Rental Python-код не импортирует Sales и использует общие Catalog/Inventory/Customer модели. Домен Rental независим, текущая сборка UI/API — нет.
- Catalog deletion импортирует SaleItem, чтобы защищать исторические ссылки; это обоснованная dependency.
- Analytics импортирует Sales и Rental как read model; это приемлемо.

============================================================
G. PAYMENT AND FISCALIZATION RELIABILITY
============================================================

G1. End-to-end flow

1. Cart
   HTTP -> SaleService. Sale row блокируется FOR UPDATE. Commit на команду.

2. Start card checkout
   HTTP -> _prepare_payment. PaymentAttempt(PENDING) и PaymentJob(QUEUED) создаются одним commit.

3. Queue wakeup
   Выполняется после commit. Redis failure допустим: 15-секундный DB sweep должен подобрать job.

4. Acquiring POST
   Worker -> process_payment() -> AQSI purchase.

5. Persist operation ID
   Отдельный DB commit после provider response.

6. Payment polling
   Worker, восемь проходов; затем job requeue.

7. Approval
   В одном DB transaction фиксируются payment succeeded, Sale paid, stock movements, fiscalization и fiscal job.

8. Receipt create/poll
   Отдельный fiscal worker job.

9. Completion
   Fiscal succeeded -> Sale completed.

10. UI
    Только GET /api/sales/{id}; provider calls из браузера отсутствуют.

G2. Reliability findings

- VERIFIED — Browser independence: navigation/закрытие страницы прекращает только визуальный polling; worker продолжает.
- VERIFIED — Durable handoff: payment approval, stock и fiscal job коммитятся совместно.
- VERIFIED — Duplicate checkout click: Sale lock и existing-attempt replay предотвращают обычный двойной POST.
- VERIFIED — Timeout payment: сохраняется UNKNOWN; blind retry блокируется.
- FAIL — Payment response/ID lost: без provider correlation исходную оплату нельзя автоматически найти; job quarantined, но оператор не получает безопасного recovery workflow.
- FAIL — HTTP 5xx: допускает новую оплату как после definitive failure.
- FAIL — Fiscal timeout/missing ID: worker автоматически повторяет create.
- FAIL — Cross-system gap: provider POST и DB commit не атомарны. При успешном POST и локальном исключении до persistence ID возможен повтор. Stale payment recovery защищает только случай, когда job остался PROCESSING; он не доказывает безопасность всех exception paths.
- UNVERIFIED — AQSI Timeout/Error: адаптер считает их definitive failure и разрешает повтор. Нужен подтверждённый acquiring contract/UAT, что банк точно не списал деньги.
- VERIFIED — Read-before-write: card fiscalization ищет receipt по slip, но lookup может быть eventually consistent; для cash lookup отсутствует. Это не exactly-once.

В тестах есть проверки browser-independent jobs, UNKNOWN payment и stale quarantine, но нет доказательства безопасного повторного запуска после receipt POST timeout/500.

- tests/test_sales_checkout.py — test_worker_requeues_temporary_fiscalization_error_without_reacquiring()
- tests/test_sales_checkout.py — test_worker_completes_fiscalization_without_browser_request()

G3. Worker and deployment

- Один RQ Worker слушает checkout и default, fork на каждую job.
- Container policy: restart: unless-stopped.
- Claims используют FOR UPDATE SKIP LOCKED.
- Stale threshold — 2 минуты; RQ job timeout — 90 секунд.
- Recovery запускается при startup и каждые 15 секунд.
- Repeat ограничен 1,000,000 запусков — примерно 174 дня непрерывной работы, затем schedule закончится без restart/re-registration.
- Graceful shutdown/lease protocol специально не реализован.

VERIFIED log:
2026-10-21 21:35:36 UTC worker упал в AQSI catalog job с:
psycopg.errors.DuplicatePreparedStatement: prepared statement "_pg3_0" already exists

INFERRED root cause:
engine.dispose() вызывается до регистрации recovery schedules, но schedule functions снова открывают DB sessions до начала RQ fork loop. Child может унаследовать повторно заполненный pool. Ошибка наблюдалась на catalog sync, а не на payment job, поэтому влияние на checkout остаётся INFERRED, но общий worker process и DB engine те же.

============================================================
H. CANCEL, REFUND AND EMERGENCY FALLBACK READINESS
============================================================

A. Cancel unpaid DRAFT
   Есть, без payment/fiscal side effects.

B. Cancel pending acquiring
   Не доступно через Sales/API/UI.

C. Reversal approved payment
   Не реализовано.

D. Refund completed payment
   Не реализовано.

E. Stop waiting in UI
   Можно уйти со страницы; операция продолжится.

F. Switch to external/manual POS
   Не реализовано для pending/unknown Sale.

AQSI adapter содержит cancel_device_operation(), но этот метод отсутствует в PaymentProvider и не вызывается Sales. Он отменяет команду устройства, а не делает банковский reversal.

Официальная AQSI API разделяет:
- POST /v4/Operations/{id}/cancel — отмена операции устройства;
- POST /v4/Slips/process/reversal — эквайринговая отмена с originalId;
- POST /v4/Slips/process/refund — возврат с originalId.

Следовательно, UI cancel нельзя интерпретировать как «деньги не списаны».

Official source: https://api.aqsi.ru/

Emergency fallback сейчас отсутствует. cash_without_receipt можно выбрать только из чистого DRAFT; он:

- записывает CASH, а не EXTERNAL_POS;
- не хранит внешнюю кассу/чек;
- не связывается с исходной UNKNOWN payment;
- не обрабатывает поздний APPROVED;
- автоматически помечает fiscalization как SKIPPED.

Одноразовый incident recovery умеет сохранять accounting_superseded, но это не штатный операторский процесс.

Требуемые safeguards:

- неизменяемая исходная UNKNOWN attempt;
- отдельное operator-confirmed external payment;
- incident/override record с actor, reason, timestamp и acknowledgement риска;
- запрет второго automatic acquiring/fiscal POST;
- связь fallback с исходной attempt;
- поздний APPROVED должен создавать reconciliation incident, а не автоматически переписывать external payment или Sale.

J. SECURITY, HISTORY, HEALTH AND OPERATIONAL CONCERNS
============================================================

J1. Security

- API key хранится encrypted и не отдаётся browser DTO: PASS.
- Provider errors sanitised/truncated: PASS.
- Sales требуют authenticated user и ограничивают Sales по owner: PASS.
- Отдельного cashier/refund/override permission нет: P1.
- Health считает глобальные payment/job состояния, хотя endpoint доступен обычному пользователю: умеренная cross-operator information leak.
- JWT хранится в sessionStorage; это увеличивает последствия XSS.

Критическая repository hygiene:

- четыре AQSI evidence/dump-файла уже staged;
- Git index mode — 100644;
- незатреканный backups/master_encryption_key-2026-10-12;
- backup paths не игнорируются.

Рабочее дерево значительно изменено и branch main ahead of origin/main на 2 commit. Аудит относится к текущему working tree, а не только к опубликованному baseline.

J2. Operation history

История может ответить:

- payment/fiscal current status — да;
- provider operation ID — да;
- external fiscal receipt ID — иногда;
- ошибки — только последнее error_code/message и job.last_error;
- operator dismissal — да, но не полноценная event history.

Не может надёжно ответить:

- был ли refund/reversal;
- какое физическое устройство выполнило конкретную операцию;
- полная последовательность ошибок;
- внешний POS и внешний receipt reference;
- связь emergency override с поздним APPROVED.

J3. Health checker

Используемые сигналы:

- AQSI Cloud list_shop_ids;
- число глобальных pending/unknown payments;
- queued/processing fiscal jobs;
- superseded operation requiring manual review.

Отсутствуют:

- device existence/online/readiness;
- worker heartbeat;
- queue lag/oldest job age;
- last successful acquiring/fiscal interaction;
- terminal busy status;
- unresolved failed fiscal jobs в общем health state.

UI отображает READY как «Касса готова», хотя backend явно проверяет только Cloud API. Это ложное усиление сигнала.

Flicker/contradictions возникают потому, что каждый rerender Sale запускает новый health request; progress polling работает каждые 0.5–2 секунды; есть 650 ms debounce, но нет request generation/abort, поэтому ответы могут применяться не по порядку. Кроме того, глобальная чужая операция может показать текущему оператору BUSY.

Минимальная семантика:

- CLOUD_UNREACHABLE;
- DEVICE_READINESS_UNKNOWN;
- PROCESSING;
- MANUAL_REVIEW;
- READY_FOR_NEW_COMMAND только после подтверждённого device signal;
- отдельный WORKER_UNHEALTHY.

K. FAILURE SCENARIO MATRIX
============================================================

1. Normal payment + fiscalization
   Current: durable jobs, stock then fiscal, Sale completion.
   Expected: то же + physical confirmation.
   Recovery: persisted job polling.
   Evidence: CheckoutService._stage_paid_sale(), run_payment_job(), run_fiscalization_job().
   Status: PASS / live UAT UNKNOWN.

2. Payment declined
   Current: AQSI Error/Canceled -> failed/canceled -> DRAFT.
   Expected: подтверждённый definitive decline.
   Risk: Error/Timeout semantics могут не доказывать отсутствие списания.
   Recovery: explicit retry только после доказанного final state.
   Evidence: AqsiCheckoutAdapter.get_payment().
   Status: UNKNOWN.

3. Provider timeout before operation ID
   Current: Payment UNKNOWN, job failed, retry blocked.
