и не изменение обычного направления интеграции CORE → AQSI.

## Правила восстановления

Инструмент `core.integrations.aqsi.incident_recovery` работает только с локальной
выгрузкой, проверенной по SHA-256. Он не создаёт платёжные/фискальные providers, не обращается
к AQSI и не ставит новые фоновые задания. По умолчанию выполняется откат; `--apply`
фиксирует всю группу одной транзакцией. Для рабочей базы API и worker останавливаются
на время применения. Блокировки таблиц защищают от конкурентной записи; изменившийся
после выгрузки состав/состояние согласованных продаж останавливает импорт.

Повторная проверка receipt ID, сумм и способов оплаты предотвращает повторный импорт.
Дополнительно проверяются чек, фискальная подпись, дата, устройство, сумма позиций,
оплаты и отдельно выгруженные слипы. Успешный `purchase` подтверждается кодом `000`
либо `SUCCESS` для `iface=sbp`, а также ссылкой из фискального чека и совпадением сумм.

Старые попытки оплаты не удаляются и не превращаются в вымышленную отмену у провайдера.
Устаревший локальный факт получает `provider_metadata.accounting_superseded=true`.
Полные прежние строки продажи, платежей, фискализации и заданий сохраняются в
`Fiscalization.provider_metadata.prior_records`, вместе с основанием, автором,
временем восстановления и хешем исходной выгрузки.

Новые успешные факты соответствуют частям реального платежа. ID слипа хранится отдельно
в `imported_slip_id`, не выдаётся за ID операции. Наличная часть имеет NULL provider.
Один фискальный факт хранит полную сумму чека и ссылки на все части оплаты.
Статистика способов оплаты суммирует `PaymentAttempt.requested_amount`, исключая
исправленные факты, а не полную сумму продажи для каждой части. Чек со смешанной оплатой
участвует в количестве чеков обоих способов; эти количества нельзя складывать.

Inventory создаёт движения только для точного Variant ID. Неопознанные позиции
остаются ручными: название не даёт права угадать SKU. Существующие движения №110
проверяются и не повторяются. Время создания движения — время восстановления;
`Sale.completed_at` и `paid_at` — время оригинального чека.

## Состояние старой операции

Локальное восстановление не доказывает отмену или завершение зависшей удалённой операции.
Её исходные status/external_id сохраняются; автоматическое продолжение прекращается.
Health возвращает `manual_review_required`, пока сохранённый старый результат неизвестен.
Баннер показывает «Требует внимания», а не обещает готовность устройства или автоматическую
проверку уже изолированного задания. Разрешение состояния AQSI — отдельное действие.

## Запуск и защита данных

1. Создать PostgreSQL backup и сохранить исходную выгрузку с закрытыми правами.
2. Проверить восстановление backup в отдельную базу.
3. Прогнать инструмент на копии, затем повторить: все чеки должны быть `already_recorded`.
4. Сделать свежий backup рабочей базы, остановить запись и применить проверенную выгрузку.
5. Проверить суммы, связи, старые продажи и Inventory. Развернуть изменения read-model/UI.

Пример вызова внутри окружения с явно выбранной базой:

```sh
python -m core.integrations.aqsi.incident_recovery /path/to/evidence.json --sha256 EXPECTED_SHA256
# Только после проверки цели и резервной копии добавить --apply.
```

Backup/выгрузки содержат рабочие и платёжные данные: **не коммитить и не публиковать**.
Dump не заменяет существующий ключ шифрования credentials из Docker volume.
Конкретные номера импортированных продаж и результаты выполнения записываются в локальный
`backups/reconciliation-2026-10-20/reconciliation-report.md`, не в публичную документацию.

## Проверки

Автотесты покрывают смешанную оплату, исправление наличного факта без удаления истории,
сохранение исходного состава, отдельный фискальный факт, однократный Inventory,
повторное применение, откат при изменённых/невалидных данных и отсутствие вызовов providers.
Проверки UI покрывают обе части смешанного платежа без исправленной старой суммы.
