# Core Business Processes

Детальные пользовательские сценарии, язык предметной области и продуктовые принципы описаны в [docs/02_user_journeys.md](02_user_journeys.md), [docs/domain.md](domain.md) и [docs/01_principles.md](01_principles.md).

## MVP scope

В первой версии Core описываются только процессы, которые нужны для запуска учета:

1. Photo-first приёмка товара с телефона.
2. Импорт существующих товаров из Tilda CSV.
3. Подготовка и отправка товаров в AQSI.
4. Первый вертикальный срез аренды оборудования как равноправного жизненного цикла.

Все остальные процессы считаются будущими расширениями.

# 1. Приемка товара с телефона

## Цель

В рамках одной Intake довести поступивший товар до состояния `ready-for-sale`: создать или найти
его каталоговую идентичность, внести все данные вариантов, промаркировать физический товар,
оприходовать его и подготовить публикацию в AQSI без обязательного перехода в Catalog.

Главное правило: Catalog не является обязательным продолжением обычной приёмки. Если оператору
нужно открыть Catalog, чтобы закончить подготовку товара к продаже, Intake workflow незавершён.

## Участник

- Manager

## Основной сценарий

1. Manager открывает Core с телефона по HTTPS и начинает или продолжает draft Intake.
2. Сканирует штрихкод, ищет существующий товар либо начинает создание нового Product.
3. Для Product указывает название, категорию, основное описание и общее фото.
4. Добавляет один или несколько поступивших Variant. Для товара без видимых вариантов существует
   один default Variant, который UI может не показывать как отдельную сущность.
5. Для каждого Variant указывает или получает SKU и barcode, добавляет фото, количество этой
   приёмки, закупочную цену, цену продажи и при необходимости rental commercial terms.
6. Сохраняет позицию Intake — Product со всеми его поступившими Variant.
7. При необходимости добавляет, редактирует или удаляет Variant, пока Intake остаётся draft.
8. Для каждого сохранённого Variant со штрихкодом открывает или печатает barcode labels до
   проведения Intake и наклеивает их на физический товар.
9. Повторяет процесс для следующих товаров.
10. Проводит Intake.
11. После успешного проведения запускает отправку всех требующих публикации Variant этой Intake
    в AQSI и видит отдельный статус каждого Variant; ошибочные публикации можно повторить.

## Результат

Во время draft Core сохраняет каталоговые данные и редактируемый состав Intake, но ещё не
создаёт фактический приход. Одна позиция Intake может включать Product с несколькими Variant.

При проведении Core в одной транзакции фиксирует:

- Product и все новые или изменённые Variant;
- связи с Product и Variant images;
- коммерческие условия Variant;
- Receipt и StockMovement для каждого принятого Variant;
- исторические закупочные факты этой поставки;
- RentalAsset, если это предусмотрено выбранным сценарием аренды.

Публикация в AQSI выполняется после проведения как отдельная повторяемая операция уровня Intake.
Сбой одного Variant не отменяет проведённый складской факт и не скрывает результаты остальных.

## Состояния и допустимые действия

```text
Draft Intake
  → добавление / редактирование / удаление Product и Variant
  → сохранение Variant identity
  → печать barcode labels
  → Complete Intake
Completed Intake
  → Inventory и закупочные факты зафиксированы
  → Publish required Variants to AQSI
  → per-variant status / retry failures
```

Barcode однозначно идентифицирует Variant. Один manufacturer barcode нельзя назначить нескольким
Variant; неоднозначный lookup и Product-level barcode пока не поддерживаются.

Camera scanning по HTTPS является deployment requirement. При недоступности камеры оператор
использует ручной ввод или аппаратный scanner.

# 2. Создание или выбор клиента

## Участник

- Оператор

## Основной сценарий

```text
Оператор
    ↓
Поиск клиента
    ↓
Клиент найден?
    ├── Да  → использовать существующую карточку
    └── Нет → создать клиента
                  ↓
Продолжить оформление аренды
```

# 3. Выдача аренды

```text
Customer
    ↓
RentalOrder
    ↓
RentalOrderItem
    ↓
RentalAsset
    ↓
Выдача
```

Workflow проверяет доступность конкретных `RentalAsset`, фиксирует оператора выдачи и изменяет
заказ и экземпляры одной транзакцией.

---

# 4. Возврат аренды

```text
RentalOrderItem
    ↓
Осмотр
    ├── исправен       → AVAILABLE
    ├── требует работ  → MAINTENANCE
    └── выведен        → RETIRED
    ↓
Закрытие заказа
```

Частичный возврат поддерживается: позиции одного `RentalOrder` могут возвращаться в разное время.
Заказ закрывается после завершения всех его позиций.
