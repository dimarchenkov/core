# Product Identifiers

## Purpose

Core assigns identifiers to every sellable `CatalogVariant`.

- SKU is a stable human-readable internal article number.
- Barcode is a replaceable operational scanner identifier.

Barcode is not the identity of Variant. Variant keeps its domain/database identity and SKU when
the operational barcode changes.

## One current operational barcode

Every Variant has exactly one current operational barcode. Its domain origin is:

- `EXTERNAL` — supplied by an operator, manufacturer or another external source;
- `INTERNAL` — generated by Core when no external barcode is supplied.

The implementation currently serializes the EXTERNAL origin with the compatibility enum value
`manufacturer`. This is terminology debt, not a second barcode kind and not a rule that every
external code must literally be assigned by a manufacturer.

The current barcode is used for:

- exact scanner lookup;
- Product labels;
- AQSI catalog projection;
- future Sales/POS lookup.

An old replaced value is not an active scanner alias. Audit/history storage may preserve the
fact that a value changed, but normal lookup resolves only `CatalogVariant.barcode`.

## Lifecycle rules

- If an operator supplies an external barcode when creating a Variant, it becomes the one current
  barcode. Core does not retain another generated barcode as an active fallback.
- If no external barcode is supplied, Core generates a current INTERNAL EAN-13.
- An EXTERNAL barcode can be replaced by another valid external barcode.
- Deleting an EXTERNAL barcode generates a fresh INTERNAL barcode and makes it current.
- An INTERNAL barcode can be replaced, but delete-to-regenerate is not a normal operation and is
  rejected by the current API.
- Current and historical barcode values are globally reserved within one Core installation and
  are not automatically reused.
- Archived Variants retain their current barcode reservation, but are excluded from normal
  scanner lookup.

The legacy `CatalogVariantBarcode` table is retained as change/audit history and compatibility
storage. Rows for retired values do not make those values active aliases.

## Internal barcode format

Core generates a 13-digit EAN-compatible Restricted Circulation Number:

```text
20 + 10-digit Core sequence + EAN check digit
```

Example:

```text
SKU-000001 -> 2000000000015
```

The `20` prefix identifies a restricted/internal number. It is suitable for use inside the
business and can be printed with EAN-13 symbology. It is not a GTIN and must never be presented as
globally unique outside the Core installation.

Core-generated values consume a monotonic sequence. A value reserved for an Intake draft or
retired after replacement is not automatically issued again.

GS1 references:

- <https://www.gs1ru.org/faq/q-myself-ean13/>
- <https://www.gs1.org/standards/id-keys/company-prefix>

## Validation and lookup

External input accepts EAN-13, EAN-8, UPC-A and printable ASCII Code 128 values. GTIN-shaped values
must have a valid modulo-10 check digit. Scanner whitespace and Enter suffixes are removed.

Normal exact lookup uses only the current barcode:

```text
GET /api/catalog/variants/by-barcode/{barcode}
GET /api/catalog/variants/lookup/by-barcode?barcode=<value>
```

The query form supports values that are inconvenient in a path. A replaced historical value does
not resolve a Variant.

## AQSI constraint

AQSI API V2 accepts a separate `sku` field and a `barcodes` array. Core sends a one-element array
containing the Variant's current operational barcode. AQSI does not choose a preferred external
code and does not receive an active internal fallback.

AQSI requires a numeric value of 4–22 digits. A current Code 128 value that does not satisfy that
channel contract makes the Variant ineligible for AQSI publication until its current barcode is
replaced; it does not authorize Core to publish a different hidden alias.

Sources:

- <https://api.aqsi.ru/>
- <https://aqsi.ru/support/dobavlenie-tovara/>

## Historical migration note

Migration `0027` introduced `catalog_variant_barcodes` by copying existing
`CatalogVariant.barcode` values. Sprint 9.11 briefly documented that collection as several active
INTERNAL/MANUFACTURER codes with a preferred-code projection. That design has been superseded by
the single-current-barcode rule above. The table remains useful for audit/compatibility, not for
multi-alias scanner lookup.
